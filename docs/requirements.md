# 基本要件

状態: 初期設計。実装・対応済み機能を示すものではない。

## 境界

新規独立サイトとして作成する。site8は変更しない。初期タイトルはガンダムカードゲーム。将来的な複数タイトルを想定し、タイトルごとのルールと大会管理を分離する。

## 利用者

| 役割 | 対象機能 |
| --- | --- |
| プレイヤー | 検索、参加登録、受付、デッキ提出、対戦確認、結果申告・確認、棄権、ジャッジ呼出、上訴 |
| 主催者 | 募集、抽選、繰上げ、受付、スタッフ権限、フェーズ設定、組合せ、順位、途中変更、告知、印刷、復旧 |
| ジャッジ | 呼出・担当管理、延長時間、裁定、ペナルティ、デッキチェック、ヘッドジャッジへの引継ぎ |

権限は大会単位で付与する。受付、スコア担当、フロアジャッジ、ヘッドジャッジを分離可能にする。兼任時の利益相反と非公開情報の閲覧範囲を扱う。

## 大会方式

以下は対応候補。公開時の対応範囲は実装・運営検証後に確定する。

- スイス、シングルエリミネーション、ダブルエリミネーション、総当たり。
- グループ予選、ブロック分割・統合、予選から決勝への進出。
- 個人戦、チーム集計戦、GCGチームバトル、多人数対戦。
- 構築、シールド、ドラフト、リーグ、サイドイベント。

大会方式、対戦単位、マッチ形式、構築形式、得点・順位基準、進行条件、デッキ運用を個別に設定する。大会を複数フェーズで構成し、進出条件、勝点・対戦履歴の持越し、デッキ再提出条件を明示する。

## 開催途中の変更

予定されたフェーズ移行、当日の方式変更、誤りの修正を区別する。変更前後の比較、影響する順位・進出者・組合せ・進行中マッチの確認、変更理由、実行者、適用開始位置、通知内容を保持する。

過去の状態を上書きして消さない。確定済みの結果や組合せに影響する変更は、対象ごとの扱いを確認して適用する。計算ルールの版、組合せの入力条件、抽選情報を保持し再現可能にする。

## 外部連携

site8を最初の連携先として想定するが、同じ公開仕様を他の開発者にも提供する。

- バージョン付きデッキ送信APIとJSONスキーマ。
- 開発者・連携アプリ登録、本人同意、OAuth 2.0 / PKCE、用途別権限。
- ゲーム識別子、構築用カード番号、印刷版、枚数、デッキ区分を表現。
- 大会サイト側で提出権限、期限、適用ルールを検証。
- 提出内容の固定スナップショット、提出版、受理結果、送信元を保存。
- 元デッキの編集・削除から提出済みデッキを独立させる。
- 再送の重複防止、締切、差戻し、再提出、公開範囲を管理。
- 署名付きWebhook、再試行、重複イベント処理、失敗状況を設計。
- OpenAPI、サンプル、検証環境、互換性方針を提供。

各サービスのDBとセッションは独立させる。アカウントは本人が明示的に連携し、メール一致で自動統合しない。公開IDや送信元URLだけを提出権限の根拠にしない。

## 共通の品質要件

- 大会操作画面の外部広告非表示と、スポンサー枠の分離。
- モバイルの参加者画面、PC中心の運営画面、ジャッジ用画面。
- 同時編集、二重送信、訂正履歴、バックアップ・復旧。
- 個人情報、非公開デッキ、裁定記録のアクセス制御。
- ルール文書・禁止制限・構築条件の版と適用日を大会に保存。
- 印刷・エクスポートによる障害時の運営継続。完全オフライン運営は別途仕様化する。
